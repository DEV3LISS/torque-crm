# Performance

All numbers measured on a MacBook (Apple Silicon), Docker Desktop, the production image from `docker compose`,
PostgreSQL 17, after loading **100 005 customers, 100 005 vehicles, 200 001 appointments** with
[`loadtests/seed-volume.sql`](../loadtests/seed-volume.sql). Reproduce with the commands in each section.

## 1. Customer search — trigram index

Query (as generated by the API): `count(*) … WHERE NOT is_archived AND lower(full_name) LIKE '%kozlova 4242%'`

| | Plan | Execution |
|---|---|---|
| Without `ix_customers_full_name_trgm` | Seq Scan, 100 005 rows filtered | **29.0 ms** |
| With trigram GIN index | Bitmap Index Scan | **5.5 ms** |

Load test [`loadtests/front-desk.js`](../loadtests/front-desk.js) — k6, 20 virtual users, 30 s, 70 % search / 20 % schedule board / 10 % availability:

| | Throughput | Search p95 | All requests p95 | Errors |
|---|---|---|---|---|
| Without trigram index | 190 req/s | 206 ms ❌ (threshold 200 ms) | 197 ms | 0 % |
| With trigram index | **1 944 req/s** | **15.8 ms** ✅ | 15.7 ms | 0 % |

The index makes the whole API ~10× faster under this mix, because slow searches were holding database connections
that the other requests needed.

**Caveat found while measuring:** for a non-selective term (`'%olga kozl%'`, 1 % of rows in the synthetic data) the
planner correctly *ignores* the index and scans — reading 1 000 matches through an index is not cheaper. Indexes
help selective predicates; always test with realistic data.

## 2. Schedule board — giving the index a lower bound

The overlap condition `starts_at < :to AND ends_at > :from` lets the `starts_at` index bound only one side, so
PostgreSQL walks every older appointment and filters it out.

| | Index Cond | Rows removed by filter | Execution |
|---|---|---|---|
| Before | `starts_at < to` | 60 336 | **10.3 ms** |
| After (`AND starts_at > from - 1 day`) | `starts_at < to AND starts_at > from - 1 day` | 141 | **0.08 ms** (~130×) |

Correctness: the domain guarantees an appointment never exceeds `Appointment.MaxDuration` (one day — it must fit
into the opening hours), so the extra predicate never drops a real overlap. Applied to the board, availability
and the utilisation report.

Reproduce: `docker compose exec -T db psql -U torque -d torque < loadtests/explain-search.sql`

## 3. Where the time goes (tracing)

With `docker compose --profile observability up`, Jaeger (http://localhost:16686) shows each request with its SQL
commands as child spans (Npgsql instrumentation) — e.g. a customer search = 1 HTTP span + 2 SQL spans (COUNT and
the page). This is the first place to look when an endpoint is slow.
